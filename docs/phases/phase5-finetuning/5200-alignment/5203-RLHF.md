## Abstract

RLHF (Reinforcement Learning from Human Feedback) is the alignment method behind ChatGPT, Claude, and Llama-2-Chat. Instead of hand-writing rules for good behavior, you collect human preference judgments, distill them into a learned reward model, and then optimize the language model against that reward with reinforcement learning (typically PPO), constrained so the model does not drift too far from its supervised starting point. RLHF is powerful but operationally heavy: it trains two models (reward model + policy), samples online during optimization, and is famously sensitive to hyperparameters. This lesson walks the full pipeline, then contrasts it with DPO ([5201](./5201-DPO-Theory.md)), which achieves a similar effect offline.

## The RLHF Pipeline

### Three Stages

```text
Stage 1: SFT                    Stage 2: Reward Model           Stage 3: RL (PPO)
+----------------+              +----------------+              +----------------+
| Pretrained LM  |              | SFT model +    |              | SFT model +    |
| + demo data    |  --------->  | value head,    |  --------->  | value head,    |
| (prompt ->     |              | trained on     |              | optimized with |
|  good response)|              | preference     |              | PPO against    |
|                |              | pairs          |              | reward model   |
+----------------+              +----------------+              +----------------+
Artifact: policy_init           Artifact: reward model R        Artifact: aligned model
```

- **Stage 1 — Supervised Fine-Tuning (SFT):** fine-tune the base model on high-quality demonstrations so it produces well-formatted, helpful responses. This is the same procedure as any instruction tuning; RLHF simply needs it as a sane starting point.
- **Stage 2 — Reward Modeling:** train a model to score `(prompt, response)` pairs so that scores reproduce human preference rankings.
- **Stage 3 — Reinforcement Learning:** treat the SFT model as a policy that "acts" by generating tokens, and optimize expected reward with PPO, penalized for diverging from the starting policy.

### Why Not Skip to RL?

```text
1. Reward signal must come from somewhere
   - Hand-written rewards (length, keywords) are gameable
   - Learned reward models capture fuzzy human judgment
2. The base model is a poor RL starting policy
   - Without SFT, outputs are malformed; PPO wastes capacity
     learning formatting instead of behavior
3. Preferences, not demonstrations, define the target
   - Demonstrations show ONE way to respond
   - Preferences say which of two responses is BETTER -
     much cheaper for humans to judge at scale
```

## Stage 2: Reward Model Training

### Data Format

Humans see one prompt and two responses, and pick a winner:

```json
{
  "prompt": "Explain recursion to a 10-year-old.",
  "chosen": "Recursion is when a function calls itself...",
  "rejected": "Recursion is a mathematical concept related..."
}
```

A preference dataset is thousands to millions of such triplets. Cost dominates: pairwise comparison is the cheapest reliable human judgment, which is exactly why the pipeline is built around it.

### Bradley-Terry Loss

The reward model outputs a scalar `R(x, y)`. We assume the probability that a human prefers `y_w` over `y_l` follows a Bradley-Terry model, and maximize the log-likelihood of the observed choices:

```text
P(y_w > y_l | x) = sigmoid(R(x, y_w) - R(x, y_l))

Loss = -E[ log sigmoid( R(x, y_w) - R(x, y_l) ) ]
```

Intuition: the loss is zero when the chosen response outscores the rejected one by a margin, and grows as the gap shrinks or inverts. The absolute scale of `R` is meaningless — only differences matter.

### Implementation

```python
from transformers import AutoModelForSequenceClassification, AutoTokenizer, TrainingArguments
from trl import RewardTrainer, RewardConfig
from datasets import load_dataset

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")
model = AutoModelForSequenceClassification.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    num_labels=1,                # scalar reward head
    torch_dtype="bfloat16",
)
model.config.pad_token_id = tokenizer.pad_token_id

dataset = load_dataset("json", data_files="preferences.jsonl")["train"]

config = RewardConfig(
    output_dir="rm-ckpt",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,
    learning_rate=5e-6,          # reward models are tuned LOW
    num_train_epochs=1,
    bf16=True,
    logging_steps=10,
)

trainer = RewardTrainer(
    model=model,
    args=config,
    train_dataset=dataset,       # columns: prompt/chosen/rejected or chosen/rejected messages
    tokenizer=tokenizer,
)
trainer.train()
```

Practical notes:

- The reward model is typically the **same size or larger** than the policy — an undersized judge is easier to fool.
- `num_labels=1` turns the sequence classifier into a scalar scorer with a fresh linear head on top of the LM backbone.
- Train for at most 1-2 epochs; reward models overfit preference noise quickly, and an overfit judge produces reward hacking downstream.

## Stage 3: PPO Optimization

### RL Framing of Generation

```text
State    s_t = prompt + tokens generated so far
Action   a_t = next token
Policy   pi(a|s) = LM softmax over vocabulary
Episode  one full generation
Reward   R(x, y) from the reward model, assigned at the
         final token (+ small per-token KL penalty)
```

The policy gradient theorem says the expected reward gradient is `E[∇log π(a|s) · A]`, where `A` is an advantage estimate. Estimating `A` needs a value function, so PPO for LMs loads a **second copy of the model with a value head** (the "critic"). Memory math: policy (bf16) + reference (bf16) + critic (bf16) + reward model ≈ 4× model weights, which is why RLHF at 70B is a data-center job.

### PPO Clipped Objective

Vanilla policy gradients take destructive steps when a single batch happens to look great. PPO limits how far one update can move the policy:

```text
ratio    r(a, s) = pi(a|s) / pi_old(a|s)      # how much more likely the
                                              # new policy makes this action
L_clip   = E[ min( r * A,
                   clip(r, 1 - eps, 1 + eps) * A ) ]

eps ~ 0.2: if the update already changed r by more
than 20%, extra improvement in that direction is
discarded instead of rewarded with a bigger step.
```

The `min` makes the objective a *pessimistic* bound: updates that would help are clipped, updates that would hurt are not encouraged either. This is the main reason PPO survives LLM training where REINFORCE diverges.

### KL Constraint

Every training batch adds a penalty proportional to how far the current policy has drifted from the frozen SFT reference:

```text
per-token penalty:  -beta * KL( pi(y|s) || pi_ref(y|s) )
typical beta:       0.02 - 0.2

Total reward = R_rm(x, y) - beta * sum_t KL_t
```

The KL term is what makes RLHF *alignment* rather than plain reward maximization: it trades a little reward for staying in-distribution, preserving fluency and instruction-following learned during SFT.

## KL Divergence and Reward Hacking

The reward model is an imperfect proxy for human judgment. Optimize it hard enough and the policy finds inputs where the proxy is confidently wrong — **reward hacking**:

```text
Classic hack patterns
- Length inflation:    longer responses score higher in RM training data
- Sycophancy:          agreeable preambles ("Great question!") correlate
                       with human ratings
- Formatting abuse:    heavy markdown/bullets mimics training data style
- Repetition loops:    certain token sequences are locally high-reward
- Distribution drift:  policy leaves the RM's training distribution;
                       RM extrapolates, exploitably
```

Detection and mitigation:

```python
# Watch these metrics every logging step:
# 1. mean KL vs reference        -> creeping up = drift
# 2. mean reward (RM score)      -> up while eval quality flat = hacking
# 3. held-out win rate vs SFT    -> the ONLY ground truth
# 4. output length distribution  -> sudden shift = length hack

# Mitigations, in order of practicality:
# - raise beta when KL slope steepens
# - early-stop on eval win-rate plateau
# - ensemble / refresh reward model with on-policy negatives
# - clip or normalize final reward
```

The tell-tale training curve: reward climbs steadily while held-out win rate plateaus (or falls) around step N. Past that point you are optimizing the proxy, not the objective.

## RLHF vs DPO

| Dimension | RLHF (PPO) | DPO ([5201](./5201-DPO-Theory.md)) |
|---|---|---|
| Models in memory | Policy + ref + critic + RM (4×) | Policy + ref (2×) |
| Sampling during training | Online generation per batch | None — offline dataset |
| Hyperparameter sensitivity | High (lr, beta, eps, batch) | Low-moderate (beta, lr) |
| Engineering complexity | High: 4 models, rollout infra | Low: one trainer loop |
| Reward model reusability | Yes — reusable for filtering/RM-guided decoding | No explicit RM |
| Ceiling | Highest when tuned well (ChatGPT-class) | Matches RLHF on many benchmarks |
| Failure signature | Reward hacking, KL blowup | Overfitting to preference noise |

Decision heuristic:

```text
Use RLHF when:
- You already operate a reward model (moderation, ranking, filtering)
- You have an RL-infra team and GPU budget for 4x memory
- You need online improvement from fresh interactions (RLAIF loops)

Use DPO when:
- First alignment pass on a new model (cheaper, stabler)
- Preference data is static and offline
- Team is small; PPO tuning expertise unavailable
```

In practice many production pipelines do **both**: a DPO pass for the bulk of alignment, then a short RLHF stage for the last few points of quality.

## Hands-On: Minimal RLHF with TRL

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
from trl import PPOConfig, PPOTrainer, AutoModelForCausalLMWithValueHead
from datasets import load_dataset

# 1. Policy (with value head) + frozen reference
model = AutoModelForCausalLMWithValueHead.from_pretrained(
    "your-org/sft-model", torch_dtype="bfloat16")
ref_model = AutoModelForCausalLMWithValueHead.from_pretrained(
    "your-org/sft-model", torch_dtype="bfloat16")
tokenizer = AutoTokenizer.from_pretrained("your-org/sft-model")
tokenizer.pad_token = tokenizer.eos_token

# 2. Prompts only — completions are generated ON POLICY each step
dataset = load_dataset("json", data_files="prompts.jsonl")["train"]

config = PPOConfig(
    output_dir="ppo-ckpt",
    learning_rate=1e-6,          # PPO lr is TINY
    batch_size=32,
    mini_batch_size=4,
    kl_coef=0.1,                 # beta: the drift constraint
    ppo_epochs=4,
)

ppo_trainer = PPOTrainer(
    config=config, model=model, ref_model=ref_model, tokenizer=tokenizer,
    train_dataset=dataset,
)

# 3. Reward: load the Stage-2 model as a scoring function
reward_model = AutoModelForSequenceClassification.from_pretrained(
    "your-org/rm-ckpt", torch_dtype="bfloat16")

for epoch in range(1):
    for batch in ppo_trainer.dataloader:
        prompts = batch["prompt"]
        gen = ppo_trainer.generate(
            ppo_trainer.prepare_inputs(prompts),
            max_new_tokens=256, do_sample=True, temperature=0.7)
        texts = tokenizer.batch_decode(gen, skip_special_tokens=True)

        with torch.no_grad():                     # score frozen RM
            rm_in = tokenizer(texts, return_tensors="pt",
                              padding=True, truncation=True).to(reward_model.device)
            rewards = reward_model(**rm_in).logits[:, 0]

        stats = ppo_trainer.step(prompts, gen, list(rewards))
        ppo_trainer.log_stats(stats, batch, rewards)
```

What to watch in `stats`: `objective/kl` (should sit near `kl_coef`'s tolerance — spiking means instability), `rewards/mean` (drifting up too fast while eval stalls = hacking), and `ratio` mean (should hover near 1.0, evidence the clipping region is being respected).

## Known Failure Modes

```text
1. Reward model overfit
   Symptom: train preference accuracy >90%, eval win rate flat
   Fix:     fewer epochs, more data, stronger regularization

2. KL collapse (policy -> reference)
   Symptom: rewards and outputs become identical to SFT
   Fix:     lower beta; check that advantage normalization is on

3. Entropy collapse
   Symptom: temperature of outputs collapses, repetitive text
   Fix:     entropy bonus, smaller lr, fewer ppo_epochs

4. Critic divergence
   Symptom: value loss explodes, advantages become noise
   Fix:     separate (lower) critic lr, gradient clipping

5. Length hack
   Symptom: mean completion length grows monotonically
   Fix:     length-normalized reward, length-balanced RM data
```
